# 함께 사용할 폴더

ChatGPT의 현재 대화가 파일 탐색·수정·검사를 판단하고, ChatSplice MCP와 Pi 실행 도구가 로컬 작업을 수행한다. Codex CLI나 다른 모델로 작업을 넘기지 않는다.

## 설정과 사용

프로젝트 설정의 **함께 사용할 폴더**에서 폴더를 직접 선택한다. 별도 ChatGPT Project를 만들거나 사이드바 프로젝트로 등록할 필요가 없다. 이미 등록된 폴더라면 그 등록 정보를 재사용한다.

- **읽기만**: 해당 폴더의 파일을 탐색·검색·읽고, 프로젝트 명령이 읽기 자료로 사용할 수 있다.
- **수정·실행**: 파일 생성·수정·이름 변경·삭제 및 해당 폴더를 기준으로 명령 실행이 가능하다.
- 기존 참조 연결은 읽기 전용을 유지한다. 사용자가 선택한 권한만 저장한다.
- 추가 폴더의 실제 파일은 연결 해제로 삭제되지 않는다.
- 같은 개발 상위 폴더를 추가하면 그 범위 안에서 하위 저장소를 찾아 사용할 수 있다. 설정 밖의 파일을 자동으로 검색하거나 권한을 부여하지 않는다.

대화 중 필요한 절대 경로를 알려주면 `fs.reference_request`로 폴더 연결을 요청한다. 새 요청은 **작업 허용**을 기본으로 제안한다. 로컬 창에서 **이 폴더에서 작업 허용**을 선택하면 그 프로젝트에서 LLM이 필요한 읽기·생성·수정·삭제·명령 실행을 판단해 수행할 수 있다. 조회만 허용하려면 **읽기 전용으로 연결**을 체크한다. 명시적 `read_only` 요청은 이 선택을 미리 체크하며 소유자가 바꿀 수 있다. 기존 연결을 자동으로 쓰기 권한으로 올리지 않는다.

승인 후에는 실제 저장된 모드를 확인하고 같은 폴더의 식별자를 계속 사용한다. 읽기·수정·검사마다 연결을 다시 요청할 필요가 없다. 권한 변경이나 다른 폴더 연결은 별도 결정이며, ChatGPT 자체의 MCP 도구 승인 설정은 이 폴더 권한과 독립적이다. 이 요청은 다른 모델을 실행하지 않는다.

응답이 끊기면 같은 요청의 같은 소유자 결정과 모드로 재시도한다. 서버가 이미 처리한 결정은 기존 결과를 반환하며 권한을 중복 적용하지 않는다. 실패 중인 첫 요청이 다른 프로젝트의 승인 요청을 계속 막지 않도록 순환 처리한다. 요청 당시의 기본 프로젝트 경로가 달라지면 이전 승인으로 새 경로에 권한을 부여하지 않는다.

## MCP 계약

`fs.reference_list`는 현재 프로젝트에 연결된 폴더의 ID, 이름, 접근 모드와 허용된 루트 경로를 반환한다. 다른 프로젝트의 바인딩은 반환하지 않는다.

일반 `fs.list/search/read/edit/write/mkdir/rename/delete`와 `project.exec`는 선택적인 `reference_workspace_id`를 받는다. 항상 원래 대화의 `workspace_id`와 `workspace_binding`을 유지한다. 경로 또는 cwd는 선택한 폴더 기준 상대경로다.

일반 파일 도구와 실행 결과의 `workspace_id/name`은 원래 프로젝트이며, 추가 폴더를 대상으로 했으면 `reference_workspace_id/name`도 반환한다. 기존 `fs.reference_paths/search/read`의 결과 형식은 유지한다.

파일 덮어쓰기는 기존의 전체 파일 SHA 검증과 원자적 교체를 사용한다. 오래된 SHA, 보호 경로, 심볼릭 링크와 파일 도구의 hard-link 제한은 그대로 적용한다. 이름 변경은 선택한 한 폴더 안에서만 수행한다.

## Pi 실행 범위

명령 실행은 기본 프로젝트와 현재 연결된 폴더의 실제 읽기·쓰기 권한을 함께 사용한다. 추가 폴더에서 명령을 시작하려면 그 폴더에 수정·실행 권한이 필요하다. 읽기 전용 폴더는 일반 프로젝트 명령의 읽기 자료로 사용할 수 있다. environment 검사는 읽기 폴더를 대상으로 할 수 있다.

추가 폴더 ID는 browser/readiness 작업에는 적용하지 않는다. 추가 폴더의 검사 성공을 기본 프로젝트의 파일만 추적하는 Goal criterion 성공으로 기록하지 않는다. 일반 지원 작업으로 Goal에 연결하는 것은 가능하다.

실행기는 raw absolute-path allowlist를 MCP 입력에서 받지 않는다. 저장된 권한을 해석해 샌드박스 규칙을 만들고, 실행 시작 직전에 다시 확인한다. 기존 private HOME/cache, host credential 차단, network 선택과 프로세스 취소/종료 처리는 유지한다. 사용자 계정 또는 관리자 권한의 전체 시스템 실행 모드를 추가한 것은 아니다.

읽기 권한은 추가 접근을 허용하는 관계다. 기본 프로젝트나 다른 쓰기 허용 폴더와 경로가 겹치면 그 기존 쓰기 권한을 취소하는 용도로 사용되지 않는다.

## 동시 작업과 권한 변경

foreground 작업은 관련 폴더를 한 번에 예약한다. 두 프로젝트가 같은 공유 폴더를 사용하는 경우에도 반대 순서로 잠금을 기다리지 않도록 묶음 예약한다. background 서버는 관련 루트의 위치를 유지하는 lease를 보유하면서 파일 편집을 허용한다.

실행 중인 관련 작업이 있으면 권한 변경·연결 해제·프로젝트 루트 변경은 busy 결과를 반환한다. 작업을 완료하거나 취소한 뒤 변경한다. 연결 해제는 이미 적용된 파일 변경을 되돌리지 않는다.

쓰기 권한은 승인 당시 source/target canonical root에 고정된다. 등록 프로젝트의 실제 폴더가 바뀌면 과거 권한으로 새 위치를 읽거나 수정하지 않는다. 설정 화면에서 변경된 경로를 확인하고 **현재 경로로 권한 다시 적용**을 누르거나 읽기 전용으로 변경한다. 네이티브 폴더 선택 창을 연 뒤 기본 프로젝트의 경로가 바뀐 경우에도 이전 선택 결과로 새 프로젝트에 권한을 연결하지 않는다.

실행 전 hard-link 검사는 읽기·쓰기 허용 루트를 한 번 순회해 실제 alias를 함께 센다. 쓰기 가능한 파일의 alias는 모두 쓰기 허용 범위 안에 있어야 하며, 읽기 전용 파일의 alias는 모두 읽기 허용 범위 안에 있어야 한다. 중첩 루트는 중복 계산하지 않고, 기존 스캔 시간·깊이·항목 한도를 유지한다.

실행 프로그램, Node runtime과 실행 파일 검색 경로에 대한 기존 신뢰 검사를 추가 쓰기 허용 폴더에도 동일하게 적용한다. 허용 폴더 안의 파일을 호스트의 신뢰된 실행 프로그램으로 취급하지 않는다.

## 적용

현재 버전은 [제품 계약](current-contract.md)에서 확인한다. 폴더 작업 승인은 control protocol 5부터 지원하며 MCP 도구 수는 24개다. 기존 reference JSON은 선택 필드가 없는 경우 읽기 전용으로 해석한다.

선택한 권한을 전달하는 새 owner control 입력은 이전 protocol 4와 혼용하지 않는다. MCP 도구 digest만 같더라도 구 daemon을 자동 재사용하거나 종료하지 않는다. 구현과 검사 범위는 [폴더 작업 승인 기록](folder-access-20261025.md)을 따른다.

소스 검사와 빌드는 실행 중인 앱을 교체하지 않는다. 미저장 작업과 실행 작업을 정리한 뒤 앱과 daemon을 정상 종료하고 새 빌드를 실행한다. 이후 연결된 MCP 정의에 `reference_workspace_id`와 요청 `access_mode`가 보이는지 확인한다. 도구 정의 갱신만으로 구 daemon의 코드가 바뀌지는 않는다.
