## Bounded code context and read completeness (2026-10-31)

MCP descriptor `0.0.21` adds optional `context_lines` (default 0, maximum 3) to `fs.search` and `fs.reference_search`. The 24 tool names, control protocol 5 and execution contract `development-runtime-4` remain unchanged. Default searches retain their existing result shape. Requested context includes numbered before/after lines for only the returned page, at most 200 UTF-16 code units plus an ellipsis per line and 16 KiB of UTF-8 context text per result. Code points are not split. `context_truncated` reports shortened or omitted context separately from discovery/resource `truncated` and ordinary `has_more` pagination. Context is a preview; exact edits still require complete current file inspection and the full-file SHA.

Search explicitly skips NUL-containing and malformed UTF-8 files. `fs.read.truncated` now includes omitted prefixes, clamps an oversized end line to real content, and preserves blank-line metadata. The original newline normalization, raw-byte file SHA, path/link/permission checks and guarded mutation flow remain in place.

This is an independent improvement informed by Serena's retrieval workflow, with no added Serena, Python or language-server dependency. The inspected Serena application is GPL-3.0-or-later while SolidLSP is MIT; no upstream source was copied. Source/API tests, staged build and the running app/remote tool catalog are distinct verification stages. See [Serena evaluation and implementation](serena-mcp-review-20261031.md).

## Folder work approval and reliable decisions (2026-10-25)

Subsequent task-directed reads, edits and checks reuse the approved relationship. Existing stored references with no mode remain read-only.

The owner decision may include `access_mode` only with approval. The chosen mode, not the initial request, determines the saved grant and approved result. A single request keeps the same owner decision through transport or busy retries. Matching simultaneous decisions share one operation; conflicting decisions are rejected before a second grant. Processing decisions do not expire midway through saving. The source root captured at submission must still match at approval. Source-root changes and project removal are blocked while a grant is being applied. Independent pending requests continue even when a prior decision cannot yet be saved.

Owner control changes are outside the MCP catalog digest, so a protocol-4 daemon is rejected at startup even if its public tool schemas match. Existing processes and jobs are not taken over. MCP descriptor 0.0.20 documents the final grant and reuse behavior; the execution contract stays `development-runtime-4` and the tool count stays 24. Apply a complete new app/daemon build after finishing current work.

Environment inspection now distinguishes an absent fixed manifest or lockfile from an invalid entry. Validated parent paths and `lstat` retain directory, symbolic-link and hard-link rejection; the inspection does not create files or run project scripts. Verification and known runtime limits are recorded in [the work report](folder-access-20261025.md).

ChatGPT's own tool consent is a separate host setting. The MCP server neither controls that prompt nor declares mutating execution read-only to suppress it. App permission preferences and high-risk exceptions are documented by OpenAI; this change affects only ChatSplice's folder grant and decision handling.

## Compact tool catalog (2026-10-22)

MCP descriptor `0.0.19` changes only the advertised tool definitions; execution contract `development-runtime-4`, control protocol 4, the 24 tool names, annotations, descriptions and result `structuredContent` remain unchanged.

- `tools/list` no longer advertises `outputSchema`. Each tool still validates its `structuredContent` against the same server-side result schema before returning it; a result outside that shape is withheld as an `INTERNAL_ERROR` tool error. This removes roughly 76 KB from the definitions sent on each connection.
- Every advertised `inputSchema` is one root object with `properties`, never a root `oneOf`/`anyOf`, because ChatGPT function definitions require a single root object. `fs.write` advertises `mode` (`create`/`replace`) with optional `expected_sha256`; `project.goal_update` advertises `action` with the union of action fields as optional properties and no defaults.
- The previous per-mode/per-action schemas are applied by the server after the advertised parse. `replace` still requires `expected_sha256` and `create` rejects it; each Goal action still requires its fields, rejects fields of other actions and applies the existing `create` defaults. Omitting `max_executions` on `resume` still preserves the stored budget. These failures return `BAD_REQUEST`.
- The desktop's expected tool schema digest is regenerated from the compiled catalog at build time. Apply it by quitting the app and daemon normally, starting the new build and refreshing the ChatGPT connection; a remote definition refresh is not observable locally.

## Execution failure diagnostics (2026-10-19)

The 2026-10-20 amendment increases command preflight's finite budget to 1,000,000 entries and 60 seconds across the union of permitted roots, retaining depth 64. These values supersede the earlier 200,000-entry and 10-second limits in historical sections below. Changing only `cwd` does not shrink that inspection. Entry, time and depth failures remain `BAD_REQUEST` and now begin with `[EXECUTION_PREFLIGHT_ENTRY_LIMIT]`, `[EXECUTION_PREFLIGHT_TIME_LIMIT]` or `[EXECUTION_PREFLIGHT_DEPTH_LIMIT]`. Messages state that the command was not started and include bounded numeric root/entry/directory/depth/elapsed/limit evidence, without file paths or contents. The generic legacy message does not identify whether entries or time exceeded its budget.

Metadata reads and final hard-link alias rechecks run in batches of at most eight, without skipping dependency/build directories, following symlinks or caching an approval. Each batch drains before failure or cancellation returns and the root lease is released. A monotonic elapsed-time check also runs after final directory I/O. This can reduce metadata latency but does not admit a tree above the entry/depth limits or forcibly interrupt an in-flight OS metadata call. Existing directory identity and writable/read-only alias completeness checks remain required.

Workbench execution history groups the current project's retained failures using known summary evidence and shows localized causes and next checks while preserving the original error and output. Stable limit tokens and the exact legacy messages are recognized; unknown failures stay unknown. Only currently retained summaries are counted: the daemon retains at most 100 jobs across projects in memory, so this is not a persistent incident archive. Evicted selections and unavailable cause filters are cleared. Network labels describe the requested operation policy (Node scripts/browser pages/local shell/readiness: loopback; Cargo: loopback with offline dependencies; install/browser setup/enabled shell: external allowed; environment: no network operation), not observed traffic or a failure diagnosis.

The 2026-10-20 progress amendment reports root/slot waiting, command preparation, file inspection and actual execution through existing message fields. Preflight notifications contain only phase and numeric evidence, at most once per 500 milliseconds apart from phase transitions; the maximum metadata batch remains eight. Root-lock waiting for direct file mutations is bounded to 15 seconds. A timed-out reservation is removed before the action can start; the deadline is cleared once acquired and never abandons an in-flight write. Local apply messages distinguish dispatcher waiting from claimed application, with elapsed time and instructions to continue the same proposal instead of submitting a duplicate.

Authenticated `/mcp` HTTP requests now receive an anonymous `x-chatsplice-request-id` response header. Structured logs correlate acceptance, the first transport error and exactly one response finish or premature close, using elapsed time and HTTP status. Request URLs, queries, headers, bodies, commands, tokens and exception text are not included. SDK adapter/handler errors use the same async request context when available. A Node response finish is not proof of client receipt or tool success; the observer neither retries nor terminates requests, and the existing disabled server-level request timeout is retained.

This adds no model call, log scraping, automatic retry/install, new MCP tool or protocol field. Browser work remains in its existing backend and selected command-preflight errors are not evidence that a model refused or that a browser action failed. The isolated renderer regression is `apps/desktop/scripts/execution-failures-ui-smoke.mjs`; use `CHATSPLICE_RENDERER_DIR` to test a separate renderer build without replacing live assets.

## Request lifecycle and evidence

Legacy workspace registries whose `kind` constraint admits only `user` and `probe` are upgraded transactionally to admit approved read-only `reference` entries. Existing IDs, roots and settings are retained; `workspaces_before_reference_kind` keeps the original registry snapshot. Fresh databases already have the current constraint. An owner decision is retained in desktop memory only for its exact pending reference-request ID, so a failed decision response retries that choice without reopening its approval dialog. Different requests still require their own approval. These changes do not alter the control protocol, MCP tools or workspace permissions.

- Use a fresh `idempotency_key` (8–96 letters, digits, `_` or `-`) per intentional operation. Reuse it only for an identical transport retry. Legacy requests without a key deduplicate by the validated bundle hash.
- Identical pending, applying and retained terminal requests return the same proposal. Reusing a key for different contents fails. Retention is memory-only, bounded to 500 terminal results and 16 MiB; after restart or eviction, deduplication is not guaranteed. Hence no unconditional idempotency annotation.
- Pending proposals expire after ten minutes. A claim that never starts returns to the queue after 30 seconds. Applying work is never requeued merely because a transport timed out.
- The owner-only `execute` endpoint returns HTTP 202. Retrying the same claim reads its existing state. The old synchronous `/v1/local-apply` and caller-supplied `/start`/`complete` endpoints are removed.
- Bundles are limited to 20 file operations, three checks and five Git commands, 900 KiB each, with a combined pending/claimed budget of 16 MiB.
- Each check/Git result carries exit code, timeout, duration, truncation and bounded stdout/stderr. File writes return their new SHA-256. The activity panel stores summaries, not these output bodies.
- A later failed step does **not** roll back earlier changes. `changed_paths`, `applied_steps` and `failed_step` describe partial execution. Re-read the affected files and correct only the remaining work.

## Files and concurrency

Foreground file mutations, owner-editor saves, bundle execution, checks/Git/execution share an exclusive canonical-root reservation. Same and nested roots serialize; independent roots can proceed. Background shell/node_script jobs and browser operations use a concurrent root lease: file edits and checks can proceed, while root replacement/removal remains blocked until cleanup. Desktop and MCP HTTP runtimes allow eight foreground executions, twelve background processes and twelve isolated browser sessions, with at most 64 queued/running jobs. Request IDs are deduplicated within their workspace; another project may independently reuse the same ID. Embedded execution-service callers retain the conservative 2/4/4/20 defaults unless they supply bounded concurrency options. SHA guards continue to detect external/server writes; a background process is not a filesystem transaction. Goal records and minimal linked receipts survive a daemon restart; live jobs, output bodies, proposals, browser sessions and images do not. Inspect files before explicitly resuming uncertain work.

Shell commands consume project-local runtime configuration (including `.env`) and may execute dependency hooks, create virtual environments and use external network. They start in a validated relative cwd with a private HOME/cache and a sanitized environment; filesystem writes remain within the workspace/private runtime, while installed language runtimes can be read. Explicit file tools retain their secret/control path and full-read/SHA policies. Browser contexts are isolated, memory-only and limited to local application navigation; they never read the ChatGPT session. Bounded screenshots are returned as MCP image content and evicted independently from metadata. These capabilities do not create a new ChatGPT turn after the conversation stops, add model allowance or bypass denied host actions.

Read, search and mutation paths reject secret/control paths after canonicalization, symbolic links and hard-linked regular files. Reads are bounded on actual bytes. Replacements recheck the SHA immediately before the atomic rename. This prevents concurrent ChatSplice lost updates; the application is not a kernel-level transaction manager against an unrelated local process swapping directories at the last instant.

The current application does not dispatch a separate Codex/Pi model worker. The Pi SDK execution adapter invokes local tooling only. A binding is a target identity, not consent to arbitrary instructions: only user-requested actions should be submitted. Earlier worker-policy and OAuth descriptions in earlier design documents do not describe this active runtime.

## Goal runtime amendment (2026-10-11)

`project.goal` reads a project's bounded Goal list or a single Goal. `project.goal_update` creates a Goal, saves a checkpoint, verifies a file criterion, pauses, explicitly resumes, cancels, completes or deletes a terminal record. Both validate the exact current workspace ID and binding. Mutations use `expected_revision`; stale revisions fail rather than overwrite another update. Daemon read-only mode permits Goal reads, pause and cancel; other Goal mutations remain blocked. The owner-only desktop API omits bindings from renderer payloads and uses its private IPC authority. The Goal workbench is a separate console tab with manual lifecycle controls; it never enters or sends a ChatGPT message.

Goals use app-private SQLite storage with a pinned canonical-root identity, immutable objective/scope/criteria, tracked file paths, checkpoint and minimal execution receipts. A display-name change preserves identity; changing or replacing the registered root blocks resume, new linked execution, evidence verification and completion through an old Goal. Metadata reads, pause and owned cancellation remain available. There is no fixed per-project or global Goal count admission cap. Each stored metadata record remains bounded to 1 MiB; list responses use at most 32 records and approximately 2 MiB per page. Each Goal tracks 1–32 regular UTF-8 paths, including file-criterion paths, with at most 1 MiB per file and 8 MiB aggregate bytes per snapshot. Missing files are represented explicitly. Traversal, secret/control paths, symlinks and hard links remain denied. Criteria are bounded to 16. Retained receipts are bounded to 128 with recent/owned/current-evidence compaction; durable request hashes preserve replay protection. Required criteria cannot be omitted. Text is caller-supplied task data; no conversation body is collected. Raw commands, stdin, output, screenshots, cookies, credentials and workspace bindings are not persisted as receipt bodies.

Criterion kinds are `file`, `check` and `browser`. File verification securely rereads the file and records its SHA. A check declares an exact existing `node_script` or fixed Cargo operation and relative cwd; a browser criterion declares a bounded assertion expectation. Optional `goal_id` and `criterion_id` on `project.exec` link a real job to its Goal. A linked criterion must match the declared operation/cwd or browser assertion; arbitrary shell/install success cannot satisfy it. Jobs without `criterion_id` may support the Goal but create no passed criterion. Evidence records the tracked-file digest, actual build/run identity, time and minimal result. Changed tracked files stale prior evidence; a different runtime build/run requires fresh check/browser evidence. A job's `succeeded` is an execution result, not Goal completion or proof of product semantics.

Creation defaults to no execution-count limit (`max_executions: 0`) and a one-hour deadline. Positive execution budgets are optional; deadlines remain one second–24 hours. Unique linked submissions consume the execution budget, and a Goal deadline bounds its linked execution timeout. Pause prevents new submissions and queued starts; already-running work can finish and retain its receipt. Cancel enters `cancelling`, cancels only owned linked jobs and reaches `cancelled` after cleanup. Other Goals, projects and human terminal sessions are unaffected. Cancellation does not roll back writes or installs. Explicit resume revalidates root and tracked files; extending its budget/deadline requires that explicit action.

On restart, uncertain queued/running receipts become `interrupted`, and active/cancelling Goals require explicit resume. No command, install, Git operation or mutation is replayed automatically. Checkpoints retain a bounded progress summary, next step and current file hashes. Read results expose current root/evidence validity so callers can distinguish saved history from present proof. Complete requires all required criteria to have current successful evidence and all owned jobs to be terminal, under the same root reservation used for project work. Failed, stale, interrupted or missing required evidence rejects completion.

The [feature backlog](feature-backlog.md) tracks implementation coverage and verification separately. Bounded retry/readiness and automatic new reasoning after a ChatGPT conversation ends remain planned or investigated. Goal persistence enables an explicit continuation within a later conversation; it does not schedule a new turn, invoke a second model or bypass account permissions. Target-account invocation and packaged-app upgrade checks remain independent gates.

## Owner control and execution-link amendment (2026-10-11)

Execution contract `goal-security-2` supersedes `goal-security-1` and `goal-environment-1`; control protocol 4, descriptor 0.0.13 and the 24 MCP tool shapes remain unchanged. Every owner control request, including status, workspace registration, binding generation, Goal/result reads, tab state, Tunnel lifecycle and shutdown, requires the existing private desktop capability before parsing or dispatch. Socket permissions and constant-time token comparison remain. Before `project.run` or command-based `project.exec` starts, a metadata-only walk checks the canonical workspace for hard-linked regular files. It never follows symlink targets and is bounded to 200,000 entries, depth 64 and ten seconds, with execution cancellation checked during traversal. Hard-linked files are allowed only when the bounded walk finds every physical alias inside the canonical workspace and revalidates each inode/link count. No unrestricted execution fallback, credential inheritance, new model or ChatGPT message is introduced. An older execution contract is rejected until the owner normally finishes work and closes its app/daemon.
